# Decisions

The rules behind Canon: what it is for, how its markup speaks, how its CSS and JavaScript are built, and what it leaves out. Each component's own rules are in its specification (`docs/components/<component>.md`).

## Vision

**The most complete, accessible plain-HTML kit for internal tools.** Canon's HTML is the only source of structure, semantics and state. Its look is one stylesheet, its behavior one optional script, and neither asks anything of the markup beyond what each component's specification documents. Because the look lives apart from the markup, a team can restyle Canon, or replace its look entirely, without touching a page.

- Scope: what internal tools need (tables, forms, records, dashboards, the shell around them). Depth over breadth: each component covers its real cases (every state and size, keyboard, right-to-left, no JavaScript) before the next one is added.
- HTML is the core product and gets the most attention. Changes to it are deliberate and versioned.
- Canon ships raw HTML only. No template helpers: any server or framework that writes HTML can use it.
- The platform first: native elements and features do the work, and canon.js fills only the gaps.

## Naming

The system is called **Canon**: the body of work accepted as authoritative within a story's universe.

- Classes: `canon-` prefix (`canon-button`, `canon-label-text`).
- CSS custom properties: `--canon-` prefix.
- Data attributes are unprefixed (`data-emphasis`); they are always scoped by a `canon-` class.

## Markup channels

| Channel | Job | Example |
|---|---|---|
| `class` | What it is (identity, slots) | `canon-button`, `canon-label-text` |
| `data-*` (enumerated) | What it means (variant axes) | `data-emphasis="high"`, `data-intent="danger"` |
| ARIA / native attributes | Semantic state | `disabled`, `aria-invalid`, `aria-busy`, `aria-pressed` |
| `data-state` | JS-only state (rare) | `data-state="open"` |

- Default emphasis is `medium`. `high` must be chosen deliberately.
- `data-size` is **optional**. Without it, the theme decides size (by default and by context).
- `data-seed` (avatars, tags) is **identity, not appearance**: a stable number from the app that a theme turns into one of its colors, the same hue on every component. Authors never pick colors. Where a color means something, it is `data-intent`; a tag takes one or the other.

## Cross-cutting conventions

- **Precedence: the author always beats the theme, but the author never has to say anything.** For optional presentation hints (`data-size`, `data-density`, `data-display`, `data-orientation`, `data-placement`): own attribute → nearest ancestor attribute → theme context → theme default. `data-gap` is the exception that isn't inherited: a Stack, Cluster or Grid takes only its own.
- **Inherited hints:** `data-size="xs|sm|md|lg|xl|2xl"`, `data-density="compact|comfortable|spacious"` and `data-display="icon"` work on containers and apply to descendants. Components with fewer sizes use their nearest (controls: xs → sm, xl and 2xl → lg).
- **Emphasis** (`high | medium | low | minimal`): how strongly an element asks for attention relative to its neighbors.
- **Intent vocabulary** (system-wide): `info | success | warning | danger`, with neutral as the default. Each component supports the subset that makes sense.
- **Icons:** HTML names the icon (`<span class="canon-icon" data-icon="trash" aria-hidden="true">`). How it's drawn (mask, background image, font) is up to the theme. The icon names Canon uses are listed in its stylesheet.
- **Indicator rule:** visuals that indicate behavior are derived from the attribute that declares the behavior (menu chevron from `aria-haspopup`, loading from `aria-busy`, external link from `target="_blank"`). They are never written in HTML.
- **Accessory position:** after the trailing icon, accepts a `canon-kbd` or a `canon-count`. Shared by buttons, nav items, tabs, menu items.
- **Theme obligations** are part of the contract (e.g. never hide a label with `display: none`).
- **Layout belongs to containers**, not components (e.g. full-width buttons). Components never set the space around themselves; [Stack, Cluster and Grid](components/stack.md) do.
- **A size hint maps to a size, never to a role.** If a theme's bigger variant means something specific (a start button, say), it is not a size and needs its own contract or container context. A theme with one size ignores the hint.
- **Sizes belong to each component.** The same `data-size` does not guarantee the same height across components (Canon's fields and buttons match; another theme's may not). Side-by-side alignment is a container's job: baseline alignment (`align-items: last baseline`) by default, and toolbar / filter bar themes may match heights inside them.
- **Hover is for pointers that hover.** A hover look (a background, a border, a color) is themed under `@media (hover: hover)`, so a tap on a touch screen doesn't leave it stuck. What hover reveals or opens (a row's actions, a toast stack, an avatar's spotlight) stays ungated: a tap is the only way to it there. A look shared with `:focus-visible` keeps its focus half outside the gate.
- **Motion by how often it's seen.** What opens from the keyboard many times a day (the Command Palette) opens at once. State changes settle without overshoot. Skeletons show only after a short wait, so quick loads never flash them.
- **Direction:** themes must use logical properties (`inline-start`, not `left`) so RTL works. Directional icon names are logical too (`arrow-forward`, `arrow-back`, not `arrow-right`), so themes can mirror them in RTL.


## CSS architecture

- Cascade layers: `@layer canon.core, canon.theme, canon.hints;`. Themes declare this order, then `@import url("canon.core.css");` (no `layer()`: core places its own rules). Unlayered app CSS beats all three, so apps can override Canon without specificity fights.
  - `canon.core`: mechanics and defaults; themes override them freely.
  - `canon.theme`: the theme.
  - `canon.hints`: author attributes (`data-size`, `data-density` (resolved to `--canon-density`: -1 / 0 / 1), `data-display`, `data-max-lines`, `data-resize`, `data-orientation` on fieldsets and sliders, `data-placement` on tooltips, `data-layout` on forms, `data-sticky` on form actions, `data-gap` on stacks, clusters and grids, `data-columns` and `data-align` on grids and clusters). Above the theme, so **"the author beats the theme" is enforced by the cascade**, not by theme discipline.
- `css/canon/canon.core.css` (optional for themes): contract mechanics with zero visual identity: size inheritance, the icon box, RTL mirroring of directional icons, button reset, visually-hidden labels and `canon-visually-hidden` (text for assistive tech only), the avatar's one-cell stack and the avatar group's row, the field grid (default: label above), the chromeless native element inside `canon-control`, textarea line math, the choice grid and the fieldset's flex layout. Every selector is wrapped in `:where()` (zero specificity).
- `attr()` reads the element the rule applies to, never a child. Prefer native sizing where it exists (an input's `size` attribute sizes it once its box shrinks to fit).
- Core's size mechanism: `data-size` (xs and sm, md, lg to 2xl) resolves theme-provided `--canon-control-*-{sm,md,lg}` tokens into `--canon-control-block-size`, `--canon-control-padding-inline`, `--canon-control-font-size`, `--canon-control-gap` and `--canon-icon-size`. Custom-property inheritance makes the nearest `data-size` win.
- `js/canon.js` (optional, `defer`): T2 behavior. **Behavior is declared with invoker commands** (`commandfor` + `command="--canon-…"`), not `onclick` or data hooks; canon.js listens for the `command` event and polyfills custom commands where invoker commands are missing. JS-driven visual state goes in `data-state`. Command buttons are hidden under `@media (scripting: none)`. Avatars whose photo fails get `data-state="error"` so the fallback shows; avatars also get their count's width (`--canon-count-inline-size`) and their seed's slot (`data-seed-slot`, from the theme's `--canon-seed-colors`; tags too) for browsers without typed `attr()` and `if()`. Tooltips use the platform's interest invokers (`interestfor` + `popover="hint"`); canon.js polyfills them where missing (hover/focus delays, hoverable tooltip, Escape, one at a time, anchoring by name), and, in every browser, names the trigger when a tooltip opens (`--canon-tooltip-anchor`) so theme arrows can aim at it: CSS can't generate unique anchor names yet. Fields with an empty message show the browser's validation there, as a danger message, instead of its bubble. Field counters (`canon-field-counter`) show how much of the control's `maxlength` is used and make it a soft limit (moved to `data-maxlength`; past it the control is invalid at once and the excess is marked), with `data-state="near"` / `"over"` and a delayed announcement. Comboboxes (`canon-combobox` around a `<select>`) get a trigger (or a text field, `data-search="inline"`), a popover list (`role="listbox"`, `aria-activedescendant`; type-ahead, or a search field with `data-search="list"`: matches marked, results announced), tags with remove buttons for `multiple`, "Add …" (`data-creatable`), `canon-search` events for app-supplied options (`data-filter="none"`, `aria-busy` while loading), `data-max` and one-row tags (`data-tags="collapse"`); the select keeps the value, validation and labels. `--canon-clear` also clears selects. Password boxes get rule checks (`data-rule`, blocking submit through `setCustomValidity`), a rules-based score (`data-score="rules"`), revealed rules (`data-reveal`), Caps Lock (`data-state="caps-lock"`), a confirmation (`data-match`) and `--canon-generate-password`. canon.js also enhances native elements that need live values CSS can't read, without markup of their own: sliders get `--canon-slider-percent` (or `-start` / `-end`), synced `<output>`s, placed marks and `aria-valuetext`.
- **Customizable select** (`appearance: base-select`) is a theme opt-in, for `pointer: fine` only. Named anchors on pseudo-elements: `anchor-scope` does not reach `::picker(select)`, so core names only the box whose select is `:open` (one at a time, so the name is unique).
- **Strings.** Text Canon produces itself (theme CSS like a link's "(opens in new tab)", canon.js announcements like "Copied") is a CSS custom property `--canon-text-<key>`. English defaults live in core; **translation files** are `i18n/<lang>.css`, switching with `:lang()`, so they follow the `lang` attribute of each element (an Arabic section inside an English page gets Arabic strings). CSS uses them with `content: var(...)`; canon.js reads them from the element it works on. One file per language (`:lang(de)` covers de-DE, de-AT, de-CH); a regional file (`de-CH.css`) loads after its base and overrides only what differs. Files coexist, so multilingual apps load several. Author-visible words (labels, "(optional)") are always the author's, never generated.
- `css/canon.debug.css` (development only, unlayered, loaded after the theme): outlines markup that breaks the contract. The reference pages turn it on with "Contract check" (`?debug`). Every new contract rule that CSS can detect gets a check here.
- **Light/dark:** the native `color-scheme` property is the switch; there is no Canon attribute. A theme declares support with `color-scheme: light dark` on `:root` and writes colors with `light-dark()`, the only CSS mechanism that follows the `color-scheme` property (a `.dark` class or `prefers-color-scheme` media query can't). `light-dark()` only accepts colors, so per-scheme values like alpha percentages must be written as two full colors.
- **Sources and builds:** the stylesheets and the script are built, not edited. Each module's code lives in `src/css/core/<module>.css`, `src/css/theme/<module>.css` and `src/js/<module>.js`; `src/css/order.json` and `src/js/order.json` keep every part in order (the cascade's; the script's single closure), and `src/manifest.json` says what each module needs. `node tools/build.mjs` writes `css/canon/canon.css`, `css/canon/canon.core.css` and `js/canon.js` with everything; `--only data-table,select --out dist` writes the three with just those components and what they need, behaving exactly as the full build; `--list` shows the bundles and the components. Bundles (`src/manifest.json`'s `bundles`) group modules as apps use them: Core, always in on the Build page, then App shell and navigation, Data Table, Date picker, Combobox, Rich Text, Color picker, Avatars, More form controls and Code Block; `--only` takes bundles and modules alike. The rules are `tools/bundle.mjs`, shared with the reference's Build page, which builds the same files in the browser (choose bundles, download the three; single components are the command line's). Build tools: Node, nothing to install. Pages always link one `canon.css` and one `canon.js`, whichever build it is.
  - In the script, a component's set-up is in the build's list only when the component is (`typeof` on a name never declared is safe), and its commands (`commands["--canon-…"]`) are registered by its own module; helpers more than one module uses live in `base`.
- **A theme is a folder:** `css/<theme>/<theme>.css`, with whatever else it needs (icons, fonts) beside it. Canon's own is `css/canon/`, which also holds the core its stylesheet imports; `css/canon.debug.css` stays outside, for any theme.
- **Canon's look:** `css/canon/canon.css`. Lucide icons at stroke 1.5, Inter (with ss01, cv02, cv03, cv04 and cv11), JetBrains Mono for code; light and dark. It declares the layers and imports the core, so it is the one stylesheet a page links.
- **Lines and depth (Canon's look):** lines inside a component (table rows, a dialog's header line, separators, the shell's edges) are hairlines: one device pixel on sharp screens (`--canon-theme-hairline`, 0.5px at 2x and up, else 1px) in see-through colors (`--canon-theme-rule`, black or white at 10%; `--canon-theme-rule-faint` for the shell, 7–8%), so they read the same on white, tints and stripes. Frames that tell people "this is a control" (text fields, checkboxes, chips) stay 1px. What floats has no frame: a hairline edge (`--canon-theme-edge`, 12%) and one of three shadows, `--canon-theme-shadow-raised` (a tooltip), `-floating` (menus, popovers, lists, popup calendars and color pickers, toasts, the bulk bar) or `-overlay` (dialogs, drawers, the command palette, the narrow sidebar). Surfaces resting on the page (Card, Table, Code Block, Alert, Menubar) have the same hairline edge instead of a frame, a Card also the raised shadow. Framed controls you click or type in (low Buttons, Button Groups, text fields) have a faint lift (`--canon-theme-shadow-control`), gone while pressed or disabled. A transparent 1px border stays under every edge, so sizes don't change and forced colors still draw a frame.
- **Supported color schemes** are declared by the theme's `color-scheme` on `:root` and read from computed style.
- **Decoration budget:** a component has more visual layers than its two pseudo-elements (on an `appearance: none` checkbox or radio too, which is how choices draw their indicators without extra markup): `background-color`, stacked `background-image` layers, `border`, `outline`, `box-shadow`. A state layer can be a `background-image` gradient over the container color, so both pseudo-elements stay free for indicators.
- **When a theme's habits conflict with the contract, the contract wins** (e.g. `pointer-events: none` belongs on `disabled` only, never on `aria-disabled`, which must stay reachable).
- Themes keep variant rules at equal specificity (`.canon-button:where(...)` that only sets local `--_*` properties), so rule order decides and disabled can simply come last.

## Contract rules

1. **No per-instance presentation options in HTML**, with these exceptions, all optional hints: `data-size`; `data-density` (how tightly things sit, independent of size: an avatar group's overlap); `data-orientation` on a fieldset (only the author knows whether the labels are short enough to share a row) or a slider (a vertical slider belongs to its layout, like a mixer); `data-placement` on a tooltip (only the author knows what it must not cover; it still flips to fit); and on a form, `data-layout="aside"` (only the author knows it is a settings page, read section by section) and `data-sticky` on its actions (only the author knows the form is long); `data-gap` on a Stack, Cluster or Grid (only the author knows how closely the things in it are related), in steps of the theme's spacing, never lengths, and `data-columns` on a Grid (only the author knows how many of its things read well side by side). Label placement, icon position and similar choices belong to the theme; density does too unless the author gives `data-density`. The markup must be structured so CSS can place things as freely as possible.
2. **Variants describe meaning, not appearance** (e.g. emphasis × intent, never "outline" or "ghost").
3. **State:** native pseudo-classes and ARIA first. When JS-driven state is unavoidable, use `data-state="…"`, never classes.
4. **System icons belong to the theme**, not the HTML.
5. **JS fallbacks are polyfills** of web standards, not custom behavior.
6. Components vital to internal tools are in; components for other kinds of sites are out (see Out of scope).
7. **The contract check** (`css/canon.debug.css`, development only) outlines breaches in a dashed amber line (the warning accent). Each check is its own rule naming its contract and its reason (`--canon-contract`, `--canon-contract-reason`), so the stylesheet is also the list of rules; one unsupported selector disables only its own check. `js/canon.debug.js` reads those rules and shows a warning for each outlined element: the contract, the reason, the exact condition it fails (and, for an unknown value, the values that are known), a floating one dismissible until the breach changes (a block has no close button: it stays while the breach does). It looks like a warning toast, with its own values so it reads the same in any theme. Where it goes: a container marked `data-canon-debug="after"` (in the docs, the playground's preview and every example frame) takes the warnings about everything inside it as blocks right after it, each naming its element (pointing at one marks the element); elsewhere a warning floats under its element in the top layer. Never inserted next to the element itself: a `<div>` there would break structures being checked (a Split Button, a list, a table).

## Out of scope

- Ripple effects (pointer-position effects in general).
- Marketing-site patterns: Canon is for internal tools and apps, so there is no Navigation Menu (top navigation with dropdown panels, mega menus), hero section or pricing table.

## Tiers

- **T0**: pure HTML/CSS
- **T1**: native platform features (popover, dialog, invoker commands, anchor positioning), polyfilled where needed
- **T2**: works without JS, enhanced with JS
- **T3**: requires JS

## Working on the docs

- `reference/<component>.html` holds the canonical markup for every variant, state and stress case: each page is a fixture a theme must render. Page chrome uses `ref-` classes and never styles `canon-` classes or sets inherited typography. Shared chrome lives in `reference/ref.js` (the top bar, navigation, example frames and playground) and `reference/ref.css`.
- Each component page has two tabs: "Reference" (the fixture) and "Playground". The Playground is a workbench: on windows wider than 56rem it fills the page under the top bar, the preview over the HTML (a divider between them drags, the arrow keys move it, a double click resets it), the controls at the end and the navigation at the start, always there to jump to another page. Wide, the Reference / Playground switch sits in the top bar after the page's name, in the same place for both views. Going to another page keeps the view: from a Playground, the next component opens on its Playground. The preview takes a width, in the URL: a ruler over the preview shows the width in its middle, a button that opens presets (full width, mobile 360, tablet portrait 720, tablet landscape 1024, desktop 1280; those wider than the preview are off), and a side at each end of the frame drags it from its middle, from 360px up to the full width, holding at a preset as it passes (the arrow keys move it too; a double click goes back to full width). Narrower than the preview, the area beyond the frame is hatched with faint diagonals. A width chosen wider than the preview shows at full width until there's room again; the divider's place is remembered in the browser. Narrower, it stacks. Each parameter gets the control that suits its options, worked out from them unless the playground names one (`widget`): meanings as colored tiles with their icons, emphasis as tiles drawing each level, icons as a field showing the chosen one that opens a grid of them, an ordered scale (sm, md, lg; compact … spacious) as a slider with a stop each, a few short options as a segmented control, numbers as a field with − and + whose label scrubs, the rest as menus, fields and switches. A changed parameter's label is in the text color; Reset puts everything back.
- **Playground:** `reference/playground/<component>.js` exports `controls` (name, label, type, options, default, group, `when`) and `render(state)` → HTML. The engine in `ref.js` renders the preview and shows the exact HTML, ready to copy. A label's note in parentheses becomes the control's tooltip and description (or, for "empty: …", its placeholder). Pattern pages have no playground.
- **Everything is in the URL** (`scheme=light|dark`, `debug`, `long-text`, `rtl`, `view`, `p.<control>`), so any configuration is a shareable link.
- **Stress modes** (from the search, or the URL): `long-text` makes every component's text on the reference about 40% longer and accented, between ⟦ and ⟧ so a clipped end shows, as translated and real-world text can be; `rtl` mirrors the fixtures. The notes, code and keys stay as they are. Empty, single-item and very long states belong to each page's own sections.
- **Navigation** lists every planned page; pages not written yet show a "Soon" Tag and are left out of Search. On narrow screens it's a drawer whose sections (Introduction, Components, Patterns) are tabs that switch its list in place.
- **Resizable demos:** a demo people drag narrower is marked `.ref-resizable` (a box around components, its start width inline or `-narrow` / `-wide`) or `.ref-resize` (on a page-like frame, its start width inline). Alone in its frame, ref.js makes the frame itself the thing you drag, with its padding: no box in a box. Give it a note of its own before it, so other demos go in other frames.
- **Static popovers:** a fixture can show popovers open (`popover="manual"` next to a `.ref-anchor[data-ref-opens="<id>"]`). ref.js opens each against its anchor when it scrolls into view and again after each scroll or resize, because anchor positioning keeps the last placement that fit.
- Built in Canon's own spirit: plain HTML, CSS and a little vanilla JavaScript.
- **Local preview:** serve the project folder over HTTP (for example `python3 -m http.server`) and open `reference/introduction.html`. Turn caching off while you work, or the browser keeps stale CSS.
