With htmx

Canon in pages that htmx updates: forms checked by the server, toasts it sends, dialogs and tables that load what they show. For adding Canon to a page, start with Getting started.

Set up

htmx swaps HTML into the page, and Canon is HTML, so the two need nothing between them: no extension, no wrapper, no build step. Load Canon as usual, then htmx:

index.html 
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/canon-ui@0.2.1/css/canon/canon.css">
<script src="https://cdn.jsdelivr.net/npm/canon-ui@0.2.1/js/canon.js" defer></script>
<script src="https://cdn.jsdelivr.net/npm/htmx.org@2.0.4/dist/htmx.min.js"></script>

Every other page here applies as it is. What follows is what changes when the server sends parts of the page instead of whole pages.

Swapped-in HTML just works

canon.js watches the page, so whatever htmx swaps in is set up the moment it lands: a Combobox gets its list, a Number Input its steppers, a Table its column widths. There's nothing to call after a swap.

Page 
<button type="button" class="canon-button" hx-get="/invoices/2041/status" hx-target="#status">
  <span class="canon-button-label">Change status</span>
</button>
<div id="status"></div>

The server answers with plain Canon markup:

Response 
<div class="canon-combobox">
  <select id="invoice-status" name="status" aria-label="Status">
    <option value="draft">Draft</option>
    <option value="sent" selected>Sent</option>
    <option value="paid">Paid</option>
  </select>
</div>

Responses are written exactly as the component pages show, so a partial your server renders for htmx is the same markup it renders into a full page.

Show that it's working

A Button with aria-busy="true" shows that it's working: the theme draws its spinner. htmx marks requests with a class of its own, so one listener turns that into Canon's attribute, for every request on the page. It's the only script this page asks for.

Once, in the layout 
<script>
  /* While a request runs, its button (or a Combobox's select) is busy:
     the theme draws a spinner, and the button can't be pressed again. */
  document.addEventListener("htmx:beforeRequest", (event) => {
    const { elt, requestConfig } = event.detail;
    const busy = requestConfig.triggeringEvent?.submitter ?? elt;
    if (!busy.matches(".canon-button, .canon-combobox select")) return;
    busy.setAttribute("aria-busy", "true");
    if (busy.matches(".canon-button")) busy.setAttribute("aria-disabled", "true");
    requestConfig.canonBusy = busy;
  });
  document.addEventListener("htmx:afterRequest", (event) => {
    const busy = event.detail.requestConfig.canonBusy;
    busy?.removeAttribute("aria-busy");
    busy?.removeAttribute("aria-disabled");
  });
</script>

A form's submit button is the one marked, also when Enter sends it. A Combobox's select shows "Loading…" in its list while its options come.

Forms and their errors

Let the server check the form and send it back. On success, the next state; with errors, the same form with each wrong field marked: aria-invalid="true" on the control, and its message with data-intent="danger". Every value comes back as typed, so nothing is lost.

Form 
<form id="invoice" hx-post="/invoices" hx-swap="outerHTML">
  <div class="canon-field">
    <div class="canon-label"><label class="canon-label-text" for="email">Email</label></div>
    <div class="canon-text-input">
      <input type="email" id="email" name="email" aria-describedby="email-message">
    </div>
    <p class="canon-field-message" id="email-message"></p>
  </div>
  <button type="submit" class="canon-button" data-emphasis="high">
    <span class="canon-button-label">Save</span>
  </button>
</form>

Sent back with an error:

Response (422) 
<form id="invoice" hx-post="/invoices" hx-swap="outerHTML">
  <div class="canon-field">
    <div class="canon-label"><label class="canon-label-text" for="email">Email</label></div>
    <div class="canon-text-input">
      <input type="email" id="email" name="email" value="ap@globex" aria-describedby="email-message" aria-invalid="true">
    </div>
    <p class="canon-field-message" id="email-message" data-intent="danger">No account uses this address.</p>
  </div>
  <button type="submit" class="canon-button" data-emphasis="high">
    <span class="canon-button-label">Save</span>
  </button>
</form>

htmx swaps only 2xx responses by default. Answer a form with errors with a 200, or let 422 swap too:

Once, in the layout 
<script>
  /* Swap 422 responses too: a form sent back with its errors. */
  htmx.config.responseHandling = [
    { code: "204", swap: false },
    { code: "[23]..", swap: true },
    { code: "422", swap: true },
    { code: "[45]..", swap: false, error: true },
  ];
</script>

The browser's own checks (required, type="email") still come first: htmx doesn't send a form the browser finds invalid, and canon.js shows the browser's message in the field. The server's errors are for what only it knows.

Toasts from the server

A Toast shows when a canon-toast event reaches the document, and htmx fires one for each name in an HX-Trigger response header. So the server can say what happened, with no script:

Response header 
HX-Trigger: {"canon-toast": {"intent": "success", "title": "Invoice saved", "description": "Sent to ap@globex.com."}}

It takes what a toast shows: intent, title, description, emphasis, timer and duration. A toast with an action (Undo) needs a function to call, so it's shown from the page's script instead: see Toast.

Dialogs that load what they show

One button opens the Dialog and asks for its content: command="show-modal" opens it at once, and htmx fills its body when the server answers. A Skeleton stands in until then.

Page 
<button type="button" class="canon-button" commandfor="edit-invoice" command="show-modal"
        hx-get="/invoices/2041/edit" hx-target="#edit-invoice-body">
  <span class="canon-button-label">Edit</span>
</button>

<dialog class="canon-dialog" id="edit-invoice" aria-labelledby="edit-invoice-title">
  <header class="canon-dialog-header">
    <h2 class="canon-dialog-title" id="edit-invoice-title">Edit invoice</h2>
    <button type="button" class="canon-button" data-emphasis="minimal" data-intent="neutral" data-display="icon"
            commandfor="edit-invoice" command="close">
      <span class="canon-icon" data-icon="close" aria-hidden="true"></span>
      <span class="canon-button-label">Close</span>
    </button>
  </header>
  <div class="canon-dialog-body" id="edit-invoice-body">
    <div class="canon-skeleton" data-shape="text"></div>
  </div>
</dialog>

Without JavaScript the button still opens the dialog. Put what it needs inside, or make the button a link to the editing page.

Tables and pages

A Table with Pagination stays plain links: each page is a real address, and works without JavaScript. hx-boost on the Pagination fetches the next page, takes only the table's part of it and updates the address, so Back and Forward work too (see Back and Forward).

Page 
<div id="invoices">
  <table class="canon-table">…this page's rows…</table>
  <nav class="canon-pagination" aria-label="Pagination"
       hx-boost="true" hx-target="#invoices" hx-select="#invoices" hx-swap="outerHTML">
    <ol>
      <li><a class="canon-pagination-prev" href="/invoices?page=1" rel="prev">
        <span class="canon-icon" data-icon="chevron-left" aria-hidden="true"></span>
        <span class="canon-pagination-label">Previous</span>
      </a></li>
      <li><a href="/invoices?page=1" aria-label="Page 1">1</a></li>
      <li><a href="/invoices?page=2" aria-label="Page 2" aria-current="page">2</a></li>
      <li><a href="/invoices?page=3" aria-label="Page 3">3</a></li>
      <li><a class="canon-pagination-next" href="/invoices?page=3" rel="next">
        <span class="canon-pagination-label">Next</span>
        <span class="canon-icon" data-icon="chevron-right" aria-hidden="true"></span>
      </a></li>
    </ol>
  </nav>
</div>

The server marks the current page (aria-current="page"), as it would for a full page. A Data Table sorts, searches and filters the rows it has; for rows the server pages, use a Table and Pagination like this.

Back and Forward

When htmx changes the address (hx-boost, hx-push-url), it keeps a copy of each page for Back and Forward, with what canon.js had drawn in it. canon.js takes its drawn parts out of the copy and sets up each component again, once, so a Combobox still has one list and a Pagination one row of pages. There's nothing to configure.

A copy shows the page as it was when people left it. For the server's latest instead (a list that may have changed meanwhile), turn the copies off, and Back fetches the page again:

Once, in the layout 
<script>
  /* Back and Forward ask the server again, instead of restoring a copy. */
  htmx.config.historyCacheSize = 0;
</script>

Options from the server

A Combobox with data-filter="none" leaves the options to the app. It fires canon-search on its select when the list opens and as people type, with what they typed in event.detail.query. htmx can take that event as its trigger:

Field 
<div class="canon-combobox" data-search="list" data-filter="none">
  <select id="country" name="country" aria-label="Country"
          hx-get="/countries" hx-trigger="canon-search" hx-vals='js:{q: event.detail.query}' hx-swap="innerHTML">
    <option value="" hidden>Choose a country</option>
  </select>
</div>

The server answers with the options that match. htmx sends the select's value along with the query, so the answer can keep the chosen option, or it's lost:

Response 
<option value="" hidden>Choose a country</option>
<option value="fi">Finland</option>
<option value="ie" selected>Ireland</option>
